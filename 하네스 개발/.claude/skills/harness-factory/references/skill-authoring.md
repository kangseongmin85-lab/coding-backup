## 1. Description
description은 스킬의 **유일한** 트리거 메커니즘이다. Claude는 보수적으로 트리거를 판단하므로 적극적("pushy")으로 쓴다.

- **나쁜 예:** `"PDF를 처리하는 스킬"`
- **좋은 예:** `"PDF 읽기·추출·병합·분할·OCR 등 모든 PDF 작업. .pdf를 언급하거나 PDF 산출물을 요청하면 반드시 이 스킬을 사용. 재실행·수정·보완 요청에도 사용."`

규칙:
- 하는 일 + 구체적 트리거 상황 + 유사하지만 트리거 안 할 경계를 모두 기술.
- **후속 작업 키워드 필수:** 재실행 / 업데이트 / 수정 / 보완 / 부분 재실행 / 이전 결과 개선 + 도메인 일상 표현. 없으면 첫 실행 후 죽은 코드가 된다.

## 2. 본문 작성 스타일
- **Why-first.** "ALWAYS pdfplumber" 대신 "테이블에는 pdfplumber를 쓴다 — PyPDF2는 행/열 구조를 보존 못 하기 때문". 이유를 알면 엣지 케이스에서 옳게 판단한다.
- **일반화.** 좁은 예시("Q4 매출 열을 변환")가 아니라 원리("수치를 암시하는 열 이름이면 숫자 타입으로 변환, 실패 시 원본 유지")로 쓴다. 오버피팅 금지.
- **명령형.** "~한다 / ~하라". 스킬은 지시서다.
- **Lean.** 본문 500줄 이내. 모든 문장이 토큰 비용을 정당화하는지 자문: Claude가 이미 아는 내용이면 삭제, 없으면 실수하는 내용이면 유지, 예시 하나가 긴 설명보다 효과적이면 예시로.

## 3. Progressive Disclosure
3단계 로딩으로 컨텍스트를 관리한다.

| 단계 | 로딩 시점 | 크기 |
|------|----------|------|
| metadata (name+description) | 항상 | ~100단어 |
| SKILL.md 본문 | 트리거 시 | <500줄 |
| references/ | 필요 시만 | 무제한 |

- 본문이 500줄에 근접하면 세부를 `references/`로 옮기고 "언제 이 파일을 읽으라"는 포인터를 남긴다.
- 300줄 넘는 reference에는 상단에 목차(ToC)를 넣는다.
- 도메인/프레임워크 변형은 `references/` 하위에 분리(예: aws.md, gcp.md)하여 관련 파일만 로드.
- 반복되는 결정적 작업은 `scripts/`에 번들링(로딩 없이 실행 가능).

## 4. 오케스트레이터 작성
오케스트레이터는 "누가 언제 어떤 순서로 협업하는가"를 담는 특수 스킬. **실행 모드를 본문 상단에 반드시 명시.**

### 에이전트 팀 모드 (기본)
```
Phase 0: 컨텍스트 확인 — _workspace/ 존재로 초기/새/부분 재실행 분기
Phase 1: 준비 — 입력 분석, _workspace/ 생성
Phase 2: 팀 구성 — TeamCreate(members: [{name, agent_type, model:"opus", prompt}])
                  TaskCreate(tasks: [{title, assignee, depends_on}])
Phase 3: 주요 작업 — 팀원 자체 조율(SendMessage), 산출물 파일 저장
Phase 4: 검증/통합 — TaskGet으로 완료 확인, Read로 수집, 통합
Phase 5: 정리 — TeamDelete, _workspace/ 보존, 결과 보고
```
필수 포함: 에이전트 구성표 / 데이터 흐름도 / 에러 핸들링표 / 테스트 시나리오(정상 1 + 에러 1).

### 서브 에이전트 모드 (대안)
팀 통신이 불필요할 때. `Agent(name, subagent_type, prompt, run_in_background:true, model:"opus")`로 호출하고 반환값 수집.

### 하이브리드
Phase마다 모드를 섞는다. 각 Phase 상단에 `**실행 모드:** {팀|서브}` 명시. 팀→서브 전환 시 반드시 TeamDelete 후 Agent 호출.

### 후속 작업 지원 (3가지 필수)
1. description에 후속 키워드 포함.
2. Phase 0에 컨텍스트 확인 — `_workspace/` 미존재=초기, 존재+부분수정=부분 재실행(해당 에이전트만), 존재+새 입력=새 실행(기존을 `_workspace_{타임스탬프}/`로 이동).
3. 각 에이전트 정의의 "이전 산출물이 있을 때" 섹션과 연동.

## 5. 데이터 전달 프로토콜
| 전략 | 방식 | 적합 |
|------|------|------|
| 메시지 기반 | SendMessage | 실시간 조율, 피드백 |
| 태스크 기반 | TaskCreate/Update | 진행 추적, 의존 관리 |
| 파일 기반 | 약속된 경로 read/write | 대용량, 구조화 산출물, 감사 추적 |
| 반환값 기반 | Agent 반환 메시지 | 서브 에이전트 결과 수집 |

규칙:
- 중간 산출물은 `_workspace/`에, 파일명은 `{phase}_{agent}_{artifact}.{ext}`.
- 최종 산출물만 사용자 지정 경로에. `_workspace/`는 보존(사후 검증·감사).
- **한 에이전트의 출력 경로 = 그것을 입력으로 쓰는 에이전트의 입력 경로.** 양쪽을 동시에 보며 일치를 확인. 불일치 = dead-link = 런타임 실패.

## 6. 흔한 실수
| 실수 | 결과 | 예방 |
|------|------|------|
| description에 후속 키워드 없음 | 첫 실행 후 죽은 코드 | 재실행/수정/보완 포함 |
| 실행 모드 미명시 | 오케스트레이터가 어떻게 도는지 불명 | 상단에 모드 명시 |
| 존재하지 않는 에이전트 이름 호출 | 런타임 실패 | agent-engineer의 name 목록 사용 |
| 출력→입력 경로 불일치 | dead-link | 데이터 흐름도와 에이전트 입출력 대조 |
| model 누락 | 품질 저하 | 모든 Agent/TeamCreate에 model:"opus" |
| 본문 500줄 초과 | 컨텍스트 낭비 | references/로 분리 |
