# 에이전트 정의 작성 표준

agent-engineer가 `.claude/agents/{name}.md`를 만들 때 따르는 표준. blueprint의 에이전트 명세를 이 구조로 구현한다.

## 표준 파일 구조

```markdown
---
name: {kebab-name}            # 파일명과 일치
description: "{1~2문장 역할 + 트리거 키워드}"
---

# {Name} — {역할 한줄 요약}

당신은 {도메인}의 {역할} 전문가입니다. {이 에이전트가 존재하는 이유 1~2문장}.

## 핵심 역할
1. ...
2. ...

## 작업 원칙
- {Why를 담은 원칙들}

## 입력/출력 프로토콜
- 입력: {어디서 무엇을}
- 출력: {어디에 무엇을 — blueprint의 출력 경로와 일치}
- 형식: {파일 포맷, 구조}

## 팀 통신 프로토콜 (에이전트 팀 모드)
- 메시지 수신: {누구로부터 무엇을}
- 메시지 발신: {누구에게 무엇을}
- 작업 요청: {공유 작업 목록에서 무엇을}

## 이전 산출물이 있을 때
- {재호출 시 기존 결과를 읽고 피드백 반영하는 방식}

## 에러 핸들링
- {실패/모호/타임아웃 시 행동}

## 협업
- {다른 에이전트와의 경계면 — 무엇으로 맞물리는가}
```

## 필수 섹션 (하나라도 빠지면 QA가 FAIL 처리)
1. frontmatter `name` + `description`
2. 핵심 역할
3. 작업 원칙
4. 입력/출력 프로토콜
5. 팀 통신 프로토콜 (팀 모드일 때)
6. 이전 산출물이 있을 때 (재호출 지침)
7. 에러 핸들링
8. 협업

## 작성 규칙
- **Why-first.** "NEVER X / ALWAYS Y" 대신 "X를 하면 Z가 깨지므로 Y한다". 이유를 알면 엣지 케이스에서 옳게 판단한다.
- **명령형 어조.** "~합니다" 대신 "~한다 / ~하라". 에이전트 정의는 지시서다.
- **이름·경로를 blueprint와 글자 그대로 일치.** 에이전트 이름은 오케스트레이터가 호출하는 경계면이다. 한 글자만 달라도 런타임에 "에이전트 없음"이 된다.
- **Lean하게.** 에이전트 정의는 "작은(역할 정의)" 문서다. 절차적 방법론은 스킬/references에 두고, 정의에는 페르소나·원칙·프로토콜만 담는다.
- **재호출 지침 필수.** 이 섹션이 없으면 후속 작업에서 매번 처음부터 다시 만든다.

## 빌트인 타입 처리
- `general-purpose`: 전체 도구(WebSearch/WebFetch 포함). 웹 조사·범용·**스크립트 실행이 필요한 QA**에 쓴다.
- `Explore`: 읽기 전용. 코드 탐색·분석. 파일 수정 불가이므로 QA에는 부적합.
- `Plan`: 읽기 전용. 설계·계획.
- 빌트인 타입이라도 `.claude/agents/{name}.md`를 만든다. 오케스트레이터가 `subagent_type: "{빌트인}"`으로 호출하고, 파일은 역할·프로토콜을 담아 재사용성과 협업 품질을 보장한다.

## 모델
- 모든 에이전트는 `model: "opus"`. 오케스트레이터의 Agent/TeamCreate 호출에서 `model: "opus"`를 명시한다. 하네스 품질은 추론 능력에 직결된다.

## 흔한 실수
| 실수 | 결과 | 예방 |
|------|------|------|
| 이름을 blueprint와 다르게 | 오케스트레이터가 못 부름 | 명세표의 name을 복사 |
| 출력 경로를 임의로 결정 | 다음 에이전트 입력과 불일치 | 명세표의 출력 경로 사용 |
| 팀 통신 대상이 추상적 | 협업이 안 일어남 | "누구에게 무엇을" 구체화 |
| 재호출 섹션 누락 | 후속 작업이 매번 새로 시작 | 8개 필수 섹션 체크 |
