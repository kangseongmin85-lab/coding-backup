## 1. 검증 우선순위
1. **경계면 정합성** (가장 높음) — 하네스 런타임 실패의 주원인.
2. **구조 정합성** — frontmatter, 필수 섹션, 커맨드 미생성.
3. **트리거 정확도** — should/should-not, 기존 스킬 충돌.
4. **드라이런 논리** — Phase 순서, dead-link, 에러 폴백.

## 2. 구조 검증
`.claude/skills/harness-factory/scripts/validate_harness.py {대상 .claude 경로}`를 실행한다. 검사 항목:
- 각 `agents/*.md`에 `name`·`description` frontmatter 존재, `name`이 파일명과 일치.
- 각 `skills/*/SKILL.md`에 `name`·`description` frontmatter 존재.
- `commands/` 디렉토리에 아무것도 없음(하네스는 커맨드를 만들지 않는다).
- 오케스트레이터 description에 후속 작업 키워드 포함.
- SKILL.md 본문 500줄 이하.
- 오케스트레이터 본문이 참조하는 에이전트 이름이 실제 `agents/`에 존재(휴리스틱 교차검사).

스크립트가 못 잡는 의미적 검증은 아래 3~5로 수동 수행한다.

## 3. 경계면 교차검증
하네스의 경계면은 다음과 같다. 각 행의 **왼쪽(생산자)과 오른쪽(소비자)을 동시에 열어** 대조한다.

| 경계면 | 왼쪽(생산자) | 오른쪽(소비자) | 불일치 예시 |
|--------|-------------|---------------|------------|
| 에이전트 호출 | 오케스트레이터 `members`/`subagent_type`/assignee의 이름 | `agents/{name}.md` 파일 | 오케스트레이터가 `analyzer` 호출, 파일은 `analyst.md` |
| 데이터 흐름 | 에이전트 A의 출력 경로 | 에이전트 B의 입력 경로 | A가 `02_a_out.md` 저장, B가 `02_analyst_out.md` 읽음 |
| 스킬 참조 | 에이전트 정의가 호출하는 스킬명 | `skills/{name}/SKILL.md` | 정의가 `/world-build` 호출, 스킬은 `world-setting` |
| Phase 의존 | 오케스트레이터 `depends_on` | 선행 Phase의 산출물 | Phase 4가 Phase 3 산출물에 의존하나 Phase 3이 그 파일을 안 만듦 |
| references 로드 | 에이전트 정의의 "Read {경로}" 지시 | 실제 references 파일 | 정의가 없는 reference를 읽으라고 지시 |

방법:
1. 오케스트레이터의 `members`·`TaskCreate` assignee에서 모든 에이전트 이름을 추출한다.
2. `agents/` 파일명 집합과 1:1로 대조한다. 호출되는데 없는 이름 → FAIL. 정의됐는데 안 불리는 에이전트 → WARN(의도 확인).
3. blueprint의 데이터 흐름도를 따라, 각 출력 경로가 그것을 입력으로 쓰는 에이전트의 입력 경로와 글자 그대로 같은지 확인한다.
4. 에이전트가 로드하라고 지시한 references/scripts 경로가 실제로 존재하는지 확인한다.

## 4. 트리거 검증
각 스킬 description에 대해:
- **should-trigger 쿼리 8~10개** — 트리거해야 하는 다양한 표현(공식/캐주얼, 명시/암시).
- **should-NOT-trigger 쿼리 8~10개** — 키워드는 유사하나 다른 도구/스킬이 적합한 near-miss.

near-miss가 핵심이다. "피보나치 함수 작성"처럼 명백히 무관한 쿼리는 가치 없다. 경계가 모호한 쿼리(예: 메타 하네스라면 "이 코드 리뷰해줘" — 하네스 구축이 아니라 일반 리뷰)가 좋은 테스트다.

기존 스킬과 트리거가 충돌하는지(같은 쿼리가 둘 다 트리거) 확인한다. 충돌 시 skill-engineer에게 description 경계 조건 강화를 요청한다.

## 5. 드라이런
오케스트레이터를 실제 실행하지 않고 논리만 따라간다:
- Phase 순서가 의존 관계와 모순되지 않는가(선행이 후행보다 먼저인가).
- 데이터 흐름에 빈 구간(dead-link)이 없는가 — 모든 입력이 이전 Phase의 출력과 매칭되는가.
- 모든 에이전트의 출력이 어딘가에서 소비되는가(고아 산출물 없음).
- 에러 시나리오별 폴백 경로가 실행 가능한가(예: 팀원 실패 → 재시도 → 누락 명시 진행).

## 6. 리포트 형식
`_workspace/05_qa_report.md`에 다음 형식으로 쓴다:

```markdown
# QA 리포트: {도메인} 하네스

## 요약
- PASS {n} / FAIL {n} / WARN {n}

## 구조 검증 (스크립트)
{validate_harness.py 출력 요약}

## 경계면 교차검증
| 경계면 | 결과 | 근거(파일:라인) | 수정 요청 대상·방법 |
|--------|------|----------------|---------------------|

## 트리거 검증
- should-trigger 통과율, 실패 쿼리
- should-NOT-trigger(near-miss) 오트리거 여부
- 기존 스킬 충돌 여부

## 드라이런
- Phase 순서/dead-link/고아 산출물/에러 폴백 점검 결과

## 미해결 항목
{1회 수정 요청 후에도 남은 결함 — 무한 루프 방지}
```

FAIL은 반드시 "파일:라인 + 무엇이 + 왜 틀렸고 + 어떻게 고친다"를 책임 에이전트에게 SendMessage한다. 경계면 이슈는 양쪽 에이전트 모두에게 알린다.
