# A/B 채점 루브릭 (산출물 확인 전 사전 고정)

대상: 두 개의 "블로그 글 작성 하네스" 산출물(harness-A, harness-B). 채점관은 어느 쪽이 무엇인지 모른다(블라인드).

각 카테고리 0~10점, 총 60점. 점수는 반드시 **근거(파일:라인 또는 구체 인용)**와 함께 부여한다. 추측·인상 금지.

## 1. 구조 유효성 (0~10)
`validate_harness.py`를 해당 하네스의 `.claude`에 실행한 결과로 채점.
- FAIL 0, WARN 0 = 10 / FAIL 0, WARN n = 10 − n (최저 6) / FAIL m 있으면 5 − m
- 실행 명령: `python "<메타하네스>/.claude/skills/harness-factory/scripts/validate_harness.py" "<대상>/.claude"`
- 스크립트 출력(PASS/WARN/FAIL 수)을 그대로 인용한다.

## 2. 경계면 정합 (0~10)
생산자·소비자를 동시에 열어 대조. 불일치 1건당 −2.
- 오케스트레이터가 호출하는 에이전트 이름 ↔ 실제 `agents/{name}.md` 파일 1:1
- 각 에이전트 출력 경로 ↔ 그것을 입력으로 쓰는 에이전트의 입력 경로 일치
- 에이전트/스킬이 참조하라는 references·스킬 경로가 실재
- 데이터 흐름의 모든 노드가 하류 소비처를 가짐(고아·dead-link 없음)

## 3. 완전성 (0~10)
- 에이전트 정의: 필수 섹션(핵심 역할/작업 원칙/입출력 프로토콜/팀 통신/재호출/에러 핸들링/협업) 충족 (누락 섹션당 −1)
- 오케스트레이터: Phase 0(컨텍스트 확인)·에이전트 구성·데이터 흐름·에러 핸들링·테스트 시나리오(정상+에러) 포함 (누락 항목당 −1.5)
- CLAUDE.md 포인터(트리거 + 변경 이력) 존재

## 4. 트리거 품질 (0~10)
- 오케스트레이터 description이 pushy하고 후속 작업 키워드 포함 (없으면 −3)
- 도메인 스킬 description이 구체적 트리거 상황 + 상호 배제 경계 포함
- should-trigger(샘플 5) / should-NOT(near-miss 5)를 채점관이 만들어 오트리거·미트리거 평가 (오답당 −1)
- 기존 스킬(harness-factory 등)과 트리거 충돌 여부

## 5. 방법론 준수 (0~10)
- 모든 Agent/TeamCreate 호출 예시에 `model:"opus"` 명시 (누락당 −2)
- 실행 모드 명시(에이전트 팀/서브/하이브리드)
- 진행적 정보 공개: SKILL.md 본문 ≤500줄, 초과 시 references/ 분리 (위반당 −2)
- `.claude/commands/`에 아무것도 없음 (있으면 −5)
- `_workspace` 파일명 컨벤션 사용
- 과도한 분리 회피(에이전트 수가 도메인 대비 적정)

## 6. 도메인 적합성 (0~10)
- 에이전트 분해가 블로그 도메인에 합당한가(리서치/작성/편집 등 자연스러운 역할)
- 생성-검증/되먹임 루프 등 품질 보장 장치 존재
- 도메인 특화 검증 기준(assertion) 또는 편집 게이트의 구체성(예: 메타설명 길이, 출처 정합, 발행본 구성요소)
- 데이터 흐름이 "주제 → 발행본"을 실제로 완성하는가

---

## 출력 형식 (채점관)
각 하네스(A, B)에 대해:

```
## Harness-{A|B}
| # | 카테고리 | 점수/10 | 근거 |
|---|---------|--------|------|
| 1 | 구조 유효성 | n | validate_harness.py: PASS x/WARN y/FAIL z ... |
| 2 | 경계면 정합 | n | ... |
| ... |
| 합계 | | nn/60 | |
```

마지막에:
- 두 하네스의 **항목별 우열**과 **총점 차이**
- 더 우수한 쪽과 그 **결정적 이유 3가지**
- 각 하네스의 **가장 약한 1가지** 결함

블라인드 유지: 어느 쪽이 어떤 방식으로 만들어졌는지 추측하지 말고, 오직 산출물 증거로만 채점한다.
